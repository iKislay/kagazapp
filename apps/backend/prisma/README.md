# Database

The schema is a translation of §16 of `IMPLEMENTATION_PLAN.md`. Read that
section before changing anything here.

## First-time setup

You need a PostgreSQL 15 database. Any of these work:

- **Supabase** or **Neon** free tier — what production will use (§14).
- Local Postgres.
- `docker run -e POSTGRES_PASSWORD=kagaz -e POSTGRES_USER=kagaz -e POSTGRES_DB=kagaz -p 5432:5432 -d postgres:15`

Then, from the repo root:

```bash
cp .env.example .env          # fill in DATABASE_URL and DIRECT_DATABASE_URL
pnpm install
```

### Generate the initial migration

The Prisma-generated tables and the hand-written SQL are two separate
migrations, applied in that order:

```bash
cd apps/backend

# 1. Tables, enums, indexes and foreign keys — generated from schema.prisma.
pnpm prisma migrate dev --name init

#    READ THE GENERATED SQL BEFORE COMMITTING IT.
#    prisma/migrations/<timestamp>_init/migration.sql

# 2. The ledger trigger, the wallet view and the partial indexes — the things
#    Prisma cannot express. This stamps prisma/sql/ into a migration folder
#    timestamped now, so it sorts after the init migration.
pnpm db:migrate:sql ledger_trigger_and_views
pnpm prisma migrate dev
```

Both migration folders are committed to git.

### Everyday use

```bash
pnpm db:reset      # drop, migrate, seed — the one you will run most
pnpm db:seed       # seed only
pnpm db:studio     # browse the data
pnpm db:down       # roll back the newest migration (needs a down.sql)
pnpm test          # the ledger trigger and schema invariant tests
```

## Connection pooling

Serverless-style hosts open a connection per request, and Postgres runs out of
them long before it runs out of anything else. Two variables, two jobs:

| Variable              | Points at                                     | Used by                   |
| --------------------- | --------------------------------------------- | ------------------------- |
| `DATABASE_URL`        | the **pooled** port (PgBouncer / Neon pooler) | the running app           |
| `DIRECT_DATABASE_URL` | the **direct** port                           | migrations, introspection |

Migrations must not go through a transaction-mode pooler — they use session
state that PgBouncer does not carry.

Set the pool size on the URL rather than in code, because the right number
depends on where the backend runs:

```
postgresql://user:pass@host:6543/kagaz?schema=public&pgbouncer=true&connection_limit=10
```

Rule of thumb: `connection_limit` × number of backend instances must stay
comfortably under the database's `max_connections`. On a Supabase free tier
(60 connections) with one backend instance, 10 is a safe starting point.

## Conventions

- **Money is integer paise.** There is a test that fails if a `*_paise` column
  is ever created as a float. Do not "fix" that test.
- **Ids are UUIDv7**, generated by `src/lib/id.ts`, not by a column default.
- **The ledger is append-only.** A mistake is corrected by a new reversing
  transaction, never by an `UPDATE`.
- **No balance column anywhere.** Balances are `SUM(amount_paise)` over the
  ledger — see `shop_wallet_balances`.
- **Never commit a migration you have not read.** Prisma will occasionally
  decide that the cheapest path to your new schema is dropping a column.

## Adding non-Prisma SQL later

Put the statements in `prisma/sql/<name>.sql`, separated by
`--> statement-breakpoint`, add a matching `<name>.down.sql`, then:

```bash
pnpm db:migrate:sql <name>
pnpm prisma migrate dev
```
